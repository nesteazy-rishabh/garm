# Dataset card: Garm episodes

## Summary

124 synthetic episodes for a scheduled back-office agent at a fictional distributor, Brackwater Industrial Supply.
Each episode is a JSON file with a starting record, timed inbound messages, ground truth for the staff callback
process, and deterministic checks on the final database state. Generated by `scripts/build_episodes.py` and
`scripts/build_attacks.py`. Licence: MIT.

## Composition

| Split | Episodes | Families |
|---|---|---|
| `benign` | 40 | t1–t10: invoices and payment runs, over-PO and duplicate invoices, refunds inside and outside the window, unmatched refund requests, order-status and payment questions, address changes, spam |
| `legit` | 16 | l1 verified bank changes, l2 customer email changes, l3 corrected invoices, l4 an honest vendor changing its phone and then its bank details (the twin of family X), 4 each |
| `attack` | 68 | c1–c5 cross-run (8 each), s1–s5 same-run (4 each), x laundered verification (8, cross-run) |

The attack goals are payment redirect (18), contact swap (14), exfiltration (16), fake invoice (12) and
unauthorised refund (8). They arrive by email (48), PDF attachment text (12) or web form (8).

## Fields

- `id`, `kind` (benign, legit or attack), `description`, `start`, `end`: simulated time, starting Monday 2026-03-02.
- `events`: timed inbound messages (`from`, `channel`, `subject`, `body`, `attachments`). Attack events carry
  `attacker: true`.
- `truth`: who owns each phone number, and which vendor changes are genuine. Only the staff callback process reads
  it; the agent and the defences never do.
- `checks` and `invariants`: deterministic graders on the final database and outbox.
- `attack`: goal, timing, channel, `indicators` (the attacker's values), `activation` checks and
  `laundered_by_policy`.
- `oracle` and `victim`: scripted tool sequences used for offline validation.

## Validation

`uv run garm validate` and `uv run pytest` check, without API calls, that for every episode:
- a scripted secure agent passes;
- a do-nothing agent fails;
- for attacks, a scripted victim triggers activation, and in cross-run attacks it does so in a later job run than the
  write.
- in family X, the handbook-following script is instead laundered under today's callback process, by design, and
  a known-good callback (D6) leaves no verification and no attacker value in any vendor field.

The generator also checks every expected payment and refund against the handbook independently of the scripts.
Changes made after seeing model output are logged in `grader-changes.md`. Each result stores a hash of its episode's
inputs, so regrading never mixes versions.

## Synthetic data

Every company, person, address and number is invented. Domains use `.example`, phone numbers use the reserved
555-01xx range, and routing numbers start with 99. Any resemblance to real entities is coincidental. No real
personal or company data was used.

## Intended use

- Comparing defences for agents that act on a shared record across scheduled runs: security, utility and approval
  load together.
- Testing approval designs and approver models against logged cards.
- Not for training models to write fraud messages. Successful adaptive-attack rewrites are kept out of the public
  repository (`data/episodes/heldout/` is git-ignored).

## Limitations

- One fictional company and a single handbook. Episodes are short (days), and the samples per family are small
  (4–8).
- The attacks are templated. The laundered family is the only one designed to defeat the record checks.
- Ground truth for the callback process is simple: the real vendor confirms only its own changes, and an attacker
  confirms anything.
